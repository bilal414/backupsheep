# BackupSheep Brand Application Plan

## Rollout principle

Apply the identity from the outside in: establish recognition and messaging first, then migrate product foundations, then add richer illustration. Do not redesign critical product flows merely to make them look new.

## Stage 1 — Brand masters

Before touching production UI:

1. Finalize Sentinel symbol.
2. Finalize wordmark.
3. Produce light/dark/monochrome variants.
4. Test favicon and repository-avatar sizes.
5. Finalize palette and typography.
6. Produce canonical architecture diagram.
7. Produce README/social preview assets.

**Exit criterion:** the identity is recognizable at 16 px and credible at hero scale.

## Stage 2 — GitHub and open-source surface

Update:

- repository avatar;
- social preview;
- README opening and lockup;
- architecture diagram;
- repository description;
- contributor documentation styling references;
- release graphic template.

The README should communicate category and recovery outcome before presenting the provider matrix.

**Exit criterion:** a first-time GitHub visitor can answer what BackupSheep is, who it is for, how it differs, and how to install it without visiting another site.

## Stage 3 — Website

### Homepage

Recommended narrative:

1. Own the way back.
2. Category and concise explanation.
3. Product screenshot/operational proof.
4. Distributed-infrastructure problem.
5. User-controlled deployment/storage.
6. Workload coverage.
7. Reliability evidence.
8. Recovery path.
9. Open-source provenance.
10. Installation CTA.

### Visual changes

- Night/Wool foundation;
- Meadow accent;
- Manrope display typography;
- Sentinel hero artwork;
- branded provider containers;
- canonical diagrams;
- restrained motion.

**Exit criterion:** marketing feels unmistakably BackupSheep without relying on the name in every viewport.

## Stage 4 — Documentation

Update documentation after the public brand surfaces so product education matches marketing.

Priorities:

- header/navigation lockup;
- architecture diagrams;
- first-run screenshots;
- backup/restore diagrams;
- immutable-copy diagram;
- deployment diagrams;
- provider icon presentation.

Documentation should remain diagram-first and task-first. Mascot use is secondary.

## Stage 5 — Console foundation

Do not begin with a page-by-page redesign. Migrate shared foundations first:

1. logo/favicons;
2. font loading;
3. brand tokens;
4. focus styles;
5. primary button;
6. selected navigation;
7. links;
8. card radius/border tokens;
9. semantic status tokens;
10. provider icon containers.

Then review dashboard, setup/onboarding, login, nodes, storage, schedules, logs, settings, and restore UI.

### Dashboard

Preserve the current operational pulse. Introduce brand through hierarchy, selected navigation, primary action, and one dark operational panel. Do not fill the dashboard with mascot artwork.

### Onboarding

This is the strongest product surface for Sentinel character. Use small illustrations to make the sequence feel approachable while preserving exact setup language.

### Login

Use the primary lockup, Wool background or quiet Night treatment, and a short product promise. Avoid decorative complexity.

### Failure states

Use operational iconography and direct copy. No mascot joke or illustration.

### Restore

Treat restore as a deliberate operational workflow. Clear source, backup date, destination/copy, overwrite behavior, and status take priority over branding.

## Stage 6 — Email and notifications

Unify:

- email logo;
- typography fallbacks;
- status iconography;
- spacing;
- success/failure/restore language.

Do not rely on brand colors or images to convey message severity.

## Stage 7 — Community and launch

Create:

- open-source relaunch graphic;
- “Own the way back” launch card;
- new integration template;
- contributor template;
- release template;
- community banner;
- optional “The Flock” community identity layer.

This is where the mascot can be most expressive.

## Content migration checklist

Across website, README, docs, and product:

- use “open-source backup and recovery control plane” consistently;
- explain “control plane” in plain language near first use;
- distinguish backup from recovery;
- distinguish source from destination;
- distinguish stored copy from backup run;
- distinguish console restore from provider-native cloud recovery;
- keep historical SaaS adoption clearly historical;
- keep beta status visible where maturity expectations matter.

## Rollout metrics

Brand work should be evaluated using product outcomes, not aesthetic preference alone.

Track where practical:

- README → installation-doc click-through;
- website hero → install/source CTA rate;
- successful first-run wizard completion;
- time to first configured source;
- time to first completed backup;
- documentation search/exit patterns;
- GitHub stars/forks/contributor activity around launch;
- qualitative feedback: “what do you think BackupSheep does?”

The most important comprehension test is whether a new technical user describes BackupSheep as a self-hosted control plane for backup/recovery rather than simply “cloud backup storage.”
