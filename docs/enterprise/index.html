The operating contract

Four questions every backup must answer

A backup product earns trust by making uncertainty visible. Use these questions during design review, incident response, and recovery rehearsal.

A

What was accepted?

A durable request, source, policy occurrence, and correlation ID must exist before queue delivery is treated as successful.

B

What was created?

Archive identity, provider resource ID, checksum, byte count, object version, or a reconciliation record—not only a provider display name.

C

Where are the usable copies?

Each destination has its own storage-point state. A partial run identifies the good copies and the copies that need attention.

D

Has recovery been proven?

Only a restore to an isolated target plus independent data verification demonstrates recoverability for that source and path.

Objects and boundaries

What each record means

Account

The tenant boundary for connections, nodes, storage, schedules, activity, notification channels, and memberships. Switching the current account changes scope; it does not move data.

Tenant-owned

Connection

Account-scoped encrypted credentials plus provider/source settings. Validation exercises the adapter but does not prove a backup or restore.

Secret-bearing

Node

A protected workload: a cloud resource, volume, website, database, or Basecamp selection. Node settings define what the backup engine should include.

Protection scope

Schedule

A database-backed policy that binds nodes, timing, destination copies, retention, and notification behavior. An on-demand run still produces the same durable backup records.

Policy

Backup request

The accepted intent and dispatch outbox. It survives a publish failure and lets recovery republish work without inventing a second request.

Durable intent

Backup & execution

The customer-visible run and its operational ledger: correlation, phase, attempts, leases, errors, provider identity, progress, artifact evidence, and reconciliation.

Durable outcome

Artifact

A verified archive generation with exact filenames, hashes, sizes, and source binding. Provider-native backups instead bind to provider resource evidence.

Integrity evidence

Storage point

One concrete copy at one destination. It has independent upload, verification, download, retention, and deletion state.

Copy ledger

Restore

A separate durable operation with an explicit target, idempotency identity, execution lease, progress, retry/reconciliation state, and terminal outcome. It never consumes the backup.

Recovery operation

State vocabulary

Read status as a contract, not decoration

Pending

Accepted but not yet owned by a worker. Check durable dispatch state before checking Celery.

In progress

A worker holds a renewable lease and should heartbeat while a bounded phase is active.

Retrying

The error is classified as retryable and the next eligible time should be visible.

Partial

At least one destination succeeded and at least one failed. Good copies remain cataloged, but direct BSE1 download is disabled and built-in website/database restore currently requires Complete.

Complete

The implemented terminal contract passed. Restore proof remains a separate requirement.

Manual review

Ownership or outcome is ambiguous. Inspect exact provider identities; do not repeat the mutation by hand.

Vocabulary stays stable across UI and API.

The console presents these objects as sources, policies, runs, copies, and recovery operations. API names may expose implementation families, but account scope and durable identifiers remain the same.

Isolation invariant

Private lanes; ciphertext-only crossings

Do not replace the one-host named-volume model with one shared filesystem. A reviewed multi-host design must preserve private lane ownership and equivalent fenced, one-way ciphertext transport. Local Storage remains storage-only.

Archive-producing flow

From request to verified copies

  1. 01
    Accept and commit

    Create durable request/correlation state before relying on broker publication.

  2. 02
    Claim and fence

    The correct queue worker acquires a renewable lease; stale owners cannot write competing terminal state.

  3. 03
    Collect or snapshot

    The source adapter performs the bounded source operation and records safe progress.

  4. 04
    Seal and verify

    The source lane creates an authenticated BSE1 envelope with its lane-local root-key ring, then publishes only fenced ciphertext.

  5. 05
    Fan out ciphertext copies

    Storage has no artifact keyring; one storage point per requested destination progresses independently through upload and readback verification.

  6. 06
    Finalize visibly

    All success → Complete; mixed outcome → Partial; no usable destination → Upload Failed.

Implemented

API clients send Authorization: Token <key>. Current persistent tokens survive browser logout and password reset; revoke or rotate them explicitly.

Current-account and visible-node scoping is the intended contract. Authorization code is under active remediation; run a complete owner/team/client role matrix against the exact released build.

Do not rely on

Multi-factor authentication

MFA-labeled API actions exist, but the current member model and login path do not implement an enforceable second factor. Treat MFA as unavailable until implemented and independently tested.

Application-level protection

Encrypted credentials

Most source/destination credentials use a per-account key that co-resides with ciphertext in PostgreSQL. Email-provider credentials use material derived from DJANGO_SECRET_KEY. This is separate from BSE1 artifact-key custody; Slack currently has plaintext exceptions.

Operator owned

TLS termination

The app speaks HTTP. A trusted reverse proxy must terminate TLS, overwrite forwarded headers, and keep port 8000 private.

Operator owned

Infrastructure encryption

Disk, database, broker, backup-media, and secret-manager encryption are deployment responsibilities.

Operator owned

Central audit and alerting

Activity and service logs exist; external retention, SIEM export, dependency metrics, and restore monitoring are not bundled.

Mutation safety

Destructive scope is explicit

Common lifecycle

How a native backup works

  1. 01
    Resolve exact source

    Bind the BackupSheep node to the current provider account, project/region, resource type, and provider identifier.

  2. 02
    Reject overlap

    Active statuses and durable request uniqueness prevent a second backup for the same node from starting concurrently.

  3. 03
    Persist intent

    Create request, backup, execution, correlation, and ownership marker before crossing a provider mutation boundary.

  4. 04
    Create once

    Ask the provider for the snapshot/image/backup using bounded timeouts and integration-specific metadata.

  5. 05
    Record provider pointer

    Persist the returned operation, resource, snapshot, job, or recovery-point identity as soon as it is known.

  6. 06
    Poll without duplicating

    Read provider status until terminal. Rate limits and temporary failures schedule later polling against the same row.

  7. 07
    Reconcile ambiguity

    If a response is lost, inventory by exact marker/account/scope. Zero, multiple, or mismatched candidates stop for review.

  8. 08
    Finalize evidence

    Store terminal provider status and identity; notify, log, and apply schedule retention only from the owned result.

The lost-response problem

A timeout does not mean “not created”

If the network fails after the provider accepts a create call, blindly retrying can create a duplicate snapshot or billable restore target. BackupSheep records mutation intent and attempts to reconcile a uniquely owned candidate before deciding what comes next.

Exact one candidate

Adopt its provider ID and continue polling the same execution.

No candidate, safe rejection proven

The adapter may permit the same durable row to retry.

Zero with uncertainty, multiple, or mismatch

Move to manual review; preserve evidence and do not guess.

Operator rule

Never “help” by creating a similarly named resource

Manual provider actions can defeat the ownership marker and duplicate guard. Work from the exact correlation ID, account/project boundary, and persisted provider identifiers.

Archive protection

Website backups turn remote trees into verified, portable archives

BackupSheep connects by FTP, FTPS, or SFTP; applies explicit path and filter rules; collects or remotely packages the selected tree; produces a ZIP plus manifest evidence; and fans the result out to every requested storage destination.

Selection contract

Scope the tree before scheduling it

  • Protect all paths or an explicit selected path set.
  • Apply include/exclude lists, glob patterns, and regular expressions.
  • For tar-mode nodes, exclude version-control ignores/metadata, caches, or existing backup files when appropriate.
  • Test the rules against a disposable tree with known included and excluded markers.
  • Record source filesystem semantics—case sensitivity, symlinks, permissions, and timestamp behavior.

Restore consequence

Selection becomes recovery scope

A beautifully completed archive cannot restore paths that were never selected. Treat filters as policy, review them after application releases, and verify the restored manifest.

Connection modes

Prove both the network path and data privileges

Direct

Worker reaches the database host/port directly. Optional database TLS settings still apply.

  • Bounded connect/statement/lock timeouts
  • Source allowlist/firewall required
  • No SSH trust layer

SSH tunnel

Worker establishes account-scoped SSH trust and forwards the database connection through the reviewed host.

  • Password, customer key, or single-account database-worker identity
  • Exact approved fingerprint required
  • Both SSH and database timeouts apply

Backup scope

Database and table selection are policy

  • Protect one database or all discovered databases.
  • Use explicit database/table selection where supported.
  • Choose stored-routine inclusion and engine-specific dump options deliberately.
  • Exclude system databases and ephemeral schemas unless recovery requires them.
  • Revalidate discovery after application migrations or tenant onboarding.

Consistency

Logical dumps observe a live system

Transaction/isolation behavior and application writes affect consistency. Define whether the chosen engine/options meet application-level recovery requirements, especially across multiple databases.

Execution pipeline

Dump, sanitize failure, verify, then replicate

  1. 01
    Validate endpoint and selection

    Reject unsupported/empty/cross-account selection before a long command starts.

  2. 02
    Acquire execution lease

    Bind the files on disk and terminal writes to one durable worker generation.

  3. 03
    Run engine-native dump

    Use selected client, safe command construction, bounded runtime, and a private work path.

  4. 04
    Build and verify archive

    Confirm expected payload, file metadata, size/hash, and exact artifact-generation binding.

  5. 05
    Fan out storage copies

    Upload each storage point independently; preserve good copies when another destination fails.

  6. 06
    Finalize and clean work files

    Only after all accepted destination states are terminal and fenced.

Current PostgreSQL direct-mode limitation.

The API/model can represent all-database or selected-database direct configurations, but the audited direct engine has no matching dump branch and reaches empty-archive failure. Use the implemented bound-database table modes only until fixed and tested; SSH mode has broader selection handling.

Node visibility

An empty group node list means all nodes

  • The primary owner sees every node in the current account.
  • A non-owner sees the union of nodes selected across their current-account groups.

Backlog points to the constrained lane

Provider snapshot/restore polling and general work. Check outbound provider access and rate limits.

Logical dumps/restores. Check source network, client version, locks, CPU, work disk.

Website/Basecamp collection. Check account-scoped SSH approval, file count, cache, source free space.

Upload/download/finalization. A rising backlog with healthy dump lanes indicates destination throughput pressure.

Activity, notifications, pruning. Lag should not rewrite backup terminal state.

RabbitMQ boundary

Transport is important, but not authoritative

The broker persists queued messages, while the database outbox and recovery sweeps retain accepted intent. During disaster recovery, prefer a clean compatible broker unless an application-consistent broker-volume restore has been tested.

Never infer completion

Replacement-host sequence

Recover closed, verify, then reopen

  1. 1

    Prepare matching software and paths

    Use the exact-commit installer; recreate proxy/network/storage policy and restore the complete protected configuration and artifact-keyring recovery set.

  2. 2

    Restore while operations are off

    Recover PostgreSQL and the compatible broker generation under the installer-owned witnesses; do not create provider workers or Beat.

  3. 3

    Pass core one-shots

    Require staging, database/broker provisioning, migrate/seal, preflight, egress guard, and web health to pass against the restored state.

  4. 4

    Verify private lanes

    Confirm exact ownership/mounts, BSE1/artifact-key custody, Local Storage ciphertext, and no cross-lane or web /backups visibility.

  5. 5

    Reconcile before opt-in

    Inspect active/stale executions, queues, schedules, destination records, and provider identities before enabling recovery sweeps or new work.

  6. 6

    Enable and rehearse

    Use the exact installer --enable-operations opt-in, resolve unknown outcomes by evidence, and restore a known backup before reopening access.

Loss scenarios

Some keys cannot be reconstructed

Lost Django key

Sessions invalidate and stored email-provider credentials protected from that key become unreadable. Restore the exact key from custody or reconfigure affected secrets.

Lost database / account key material

Encrypted source/destination credentials may not be recoverable from ciphertext. Re-enter and revalidate every integration.

Lost onboarding token

Relevant only before initial owner creation. After onboarding, use account membership and reviewed host-side password administration.

Lost provider mapping

Do not adopt resources by name. Reconstruct only from independent exact IDs/tags/markers and reviewed ownership evidence.

BackupSheep is a self-hostable beta. The repository contains meaningful reliability engineering and dated live-test evidence, but no enterprise certification, SLA, or universal provider/scale guarantee is established by this documentation.

Current enterprise gates

Do not claim production enterprise readiness until these close

Blocker

Security and delegated authorization

Complete remediation and independent retest of legacy management authorization, action maps, membership state, token lifecycle, OAuth state binding, MFA, and secret exposure. Run cross-account/role negative tests on the final commit.

Blocker

Restore coverage truth

Certify every advertised source × destination restore path. Built-in website/database restore currently requires overall Complete; Partial copies are not accepted. Only a subset of destinations has exact authenticated materialization.

Blocker

PostgreSQL direct-mode selection

Current direct all-/selected-database modes can produce an empty-archive failure; table-selection mode is the implemented direct path. Fix and test before general PostgreSQL claims.

Open

Local restore idempotency

Website and logical database restore creation do not currently have the native restore request-idempotency/target-active guard. Repeated POSTs can create separate restore rows.

Open

Transfer-to-storage action

A transfer UI/serializer surface exists, but no complete server action/task was found in the audited path. Treat transfer as unavailable until implemented and tested.

Evidence pending

BSE1 custody boundary

The current repository implements chunked AES-256-GCM-SIV, source-lane local-file keyrings, private staging, fenced ciphertext handoff, and authenticated restore-before-write. Exact-release custody, tamper/swap, rotation, key-loss, provider, and cross-lane runtime evidence remains a release gate.

Open

Alternate deployment parity

Supported descriptors reference the durable scheduler, but they do not automatically reproduce stock Docker's file-backed secrets, identity generations, staging witnesses, egress namespaces, or operations-profile boundary. Certify them separately.

Open

Large-scale acceptance

Historical current-artifact database/small-site/Unicode gates passed, while the 100 GB single-archive and 2,000,000-file paths retained unresolved failures or incomplete remediation gates.

Shared vocabulary

Terms used across the manual

Use these definitions in runbooks, tickets, support packets, acceptance reports, and API integrations so “backup,” “copy,” “execution,” and “restore” do not collapse into one ambiguous status.

Account
The tenant boundary that owns product configuration and activity.
Artifact
A concrete archive generation bound to a source execution with recorded filenames, bytes, digests, and verification.
Backup
The customer-visible record of one protection run. It is distinct from its request, execution, artifact, and copies.
Backup request
Durably accepted intent plus dispatch/outbox state.
Connection
Account-scoped credentials and settings used to reach a source or provider.
Correlation ID
A stable, non-secret identifier connecting public status to secured operational diagnostics.
Destination
A configured location capable of storing archive copies.
Execution
The durable operational ledger for phase, ownership, attempts, retry, progress, provider identity, and reconciliation.
Fencing token
A generation/ownership value that prevents a stale worker from persisting competing state after losing its lease.
Fork restore
A logical database restore into deterministic new database names rather than overwriting source data.
Idempotency key
A caller identity that makes replay of the same supported mutation converge on the existing durable request.
Lease
Time-bounded permission for one worker to own a phase; renewed by heartbeat.
Manual review
A fail-closed terminal/holding state used when exact external ownership or outcome cannot be proven safely.
Node
A protected workload or resource selected through a connection.
Occurrence
One computed scheduled firing, with a stable identity used to converge duplicate scheduler delivery.
Overlay restore
Write archive files over matching target paths while preserving unrelated target files.
Exact-mirror restore
Make the target match the backup scope, including deletion of files absent from the archive; destructive.
Partial
An archive backup where at least one destination succeeded and at least one failed. The good copy is retained, but current website/database built-in restore requires overall Complete.
Provider-native backup
A snapshot, image, recovery point, or managed backup that remains in the connected provider account.
Reconciliation
Read-only or bounded discovery that determines whether an external mutation with an unknown response produced an exact owned result.
Recovery point objective (RPO)
The maximum acceptable age/loss window of recoverable data or control-plane state.
Recovery time objective (RTO)
The target time to restore a required service or control plane.
Restore rehearsal
A controlled recovery to an isolated target followed by independent data/application verification and owned cleanup.
Schedule
A database-backed timing, placement, and retention policy for one node.
Storage point
One independently tracked copy of an archive at one destination.
Verification
Evidence that a result satisfies a bounded integrity/identity contract; not synonymous with full application recovery.
