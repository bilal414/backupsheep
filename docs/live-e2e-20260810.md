## Expected evidence contract

The following fields are required before a website or database case can move from
`Pending` or `Observed — completion pending` to `Verified`. A field is allowed to
be `not returned by provider` only when that absence is explicitly recorded.

| Evidence area | Required fields |
| --- | --- |
| Website backup | BackupSheep backup ID; source connection and node IDs; provider/host/user/path; backup mode; request/idempotency and correlation IDs; Celery task ID; attempt, lease/fence, and final status; storage provider, bucket/container, folder/object key; provider object ID; byte count; SHA-256; ETag; version ID; content type; object existence/read-back result |
| Website restore | Restore ID/task ID; source backup/artifact ID; exact source object key and provider object ID/version ID; target connection/host/path; ownership and target-safety proof; bytes written; post-restore SHA-256 and marker comparison; final status and any provider request ID |
| Database backup | BackupSheep backup ID; connection/node ID; engine/version; endpoint/port/database; dump method and consistency marker; row/fixture marker result; dump byte count; SHA-256; storage bucket/key; provider object ID; ETag; version ID; content type; final status and retry/adoption evidence |
| Database restore | Restore ID/task ID; source artifact ID; target engine/endpoint/database or exact native provider resource ID/ARN; fork/source witness where applicable; ownership tag/label; provider request/job ID; target status; row/marker and schema checks; restored dump/data SHA-256; final status |
| Duplicate prevention and recovery | Stable request/correlation ID; single logical BackupSheep job row; Celery task identity across redelivery/restart; attempt count; durable lease/fence outcome; provider request ID; exact duplicate-match count; adoption witness; poll classification distinguishing in-progress, provider failure, 404, rate limit, and transient outage |
